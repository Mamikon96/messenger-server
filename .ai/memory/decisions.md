## SH-D01 — AI-память хранится в `.ai/memory/` в репозитории (2026-10-05)
- **Решение:** `CLAUDE.md` в корне + markdown-файлы в `.ai/memory/`; структура перенесена из frontend-проекта `messenger-client-react` (там SH-D01).
- **Почему:** общий контекст между сессиями и разработчиками, версионируется вместе с кодом; единый формат с frontend.

## SH-D02 — Приёмка задач через `bash scripts/accept.sh` (2026-10-05)
- **Решение:** задача завершена только при `bash scripts/accept.sh` = 0 и APPROVE от `nestjs-reviewer`. Сейчас скрипт проверяет память и падает, пока не заданы тесты (BE-01): «зелёной» приёмки нет, значит задач «Сделано» с приёмкой тоже нет.
- **Почему:** один детерминированный критерий готовности, как во frontend (там SH-D02); тестовый стек backend ещё не выбран.
- **Альтернативы:** считать приёмкой только проверку памяти (не проверяет код).

## SH-D03 — Проект содержит только backend (2026-10-05)
- **Решение:** в памяти одна сторона — `backend/` (ID `BE-`), без `frontend/` и `contracts.md`. Формат с подпапкой стороны сохранён, чтобы протокол `project-memory` работал без изменений. Frontend ведётся в отдельном репозитории `messenger-client-react` (его SH-D04, SH-D09).
- **Почему:** бэкенд — отдельный проект (решение владельца, SH-D09 frontend); заглушки другой стороны вводили бы в заблуждение.
- **Альтернативы:** плоская раскладка без `backend/` (ломает единый протокол скилла); монорепо с двумя сторонами (преждевременно).

## SH-D04 — Решение фиксируется сразу после выбора пользователя; пишет solution-architect (2026-10-05)
- **Решение:** после ответа пользователя на `AskUserQuestion` решение («Решение / Почему / Альтернативы») записывается в `decisions.md`: если варианты готовил `solution-architect` — он сам (основная сессия передаёт выбор через `SendMessage`), иначе основная сессия. Нет выбора — ничего не пишем.
- **Почему:** агенты читают готовые решения и не изобретают их заново; причины фиксируются, пока свежи. Перенос SH-D05 frontend.
- **Альтернативы:** запись после реализации (решения теряют контекст); отдельный вопрос «записывать ли?» (лишний шаг).

## SH-D05 — Жёсткое правило для всех агентов: сомнение или нехватка данных → вопрос пользователю (2026-10-05)
- **Решение:** любой агент при сомнении или нехватке данных спрашивает пользователя и ничего не придумывает. Правило — `.ai/rules/ask-user.md` и п. 6 «Неснимаемых правил» `CLAUDE.md`. Агент без `AskUserQuestion` возвращает вопросы вызывающему. Перенос SH-D06 frontend.
- **Почему:** догадки агентов дают неверные требования и незаметные ошибки; цена вопроса ниже цены переделки.
- **Альтернативы:** правило только в `CLAUDE.md` (агенты вне проекта его не увидят); допущения «по умолчанию» (строят работу на выдумке).

## SH-D06 — Продукт: реальный мессенджер для малой закрытой группы, бэкенд — этот проект (2026-10-05)
- **Решение:** цель — реальный мессенджер для малой закрытой группы: до ~1 000 пользователей, один сервер, TLS, без E2EE. Этот репозиторий — бэкенд; frontend — `messenger-client-react`. Соглашения — `product-agreements.md` (перенесены из frontend SH-D09).
- **Почему:** решение владельца проекта (SH-D09 во frontend); отдельные репозитории не смешивают релизные циклы.
- **Альтернативы:** публичный продукт с ростом, E2EE, корпоративный вариант (избыточны для малой группы).

## SH-D07 — Основа бэкенда: Node.js + WebSocket + PostgreSQL, фреймворк NestJS (2026-10-05)
- **Решение:** Node.js, реалтайм через WebSocket, данные в PostgreSQL (SH-D10 frontend); фреймворк — NestJS (выбор пользователя, BE-D01 ниже). Остальные библиотеки (ORM/драйвер, WebSocket-слой, тестовый стек) — отдельно по `tech-approval.md`.
- **Почему:** контроль и совместимость с контрактом BFF/OAuth из frontend; для ~1 000 пользователей объём невелик.
- **Альтернативы:** BaaS (Supabase/Firebase), Matrix (Synapse), «только клиент на mock-сервере» — отклонены во frontend SH-D10.

## BE-D01 — Фреймворк бэкенда: NestJS (2026-10-05)
- **Решение:** бэкенд на NestJS (Node.js + WebSocket + PostgreSQL по SH-D07). Выбор сделан пользователем при создании структуры памяти.
- **Почему:** пользователь причину не называл (не записываем догадок); при необходимости уточнить.
- **Альтернативы:** Next.js route handlers, Node.js + Fastify/Express — предлагались, не выбраны.

## SH-D08 — Плоская раскладка памяти: без подпапки `backend/` (2026-10-05)
- **Решение:** файлы `state.md`, `tasks.md`, `architecture.md` лежат прямо в `.ai/memory/`, решения backend (`BE-Dxx`) — в общем `decisions.md` вместе с `SH-Dxx`. Подпапка `backend/` удалена. Уточняет SH-D03 в части раскладки (одна сторона, подпапка не нужна); скилл `project-memory` поддерживает плоскую раскладку.
- **Почему:** решение владельца проекта; проект односторонний, подпапка стороны не несла смысла; два `decisions.md` дублировали бы друг друга.
- **Альтернативы:** оставить `backend/` (совпадает с frontend, но лишний уровень); два файла решений с разными именами (два места для решений).
