## SH-D01 — AI-память хранится в `.ai/memory/` в репозитории (2026-10-05)
- **Решение:** `CLAUDE.md` в корне + markdown-файлы в `.ai/memory/`; структура перенесена из frontend-проекта `messenger-client-react` (там SH-D01).

## SH-D02 — Приёмка задач через `bash scripts/accept.sh` (2026-10-05)
- **Решение:** задача завершена только при `bash scripts/accept.sh` = 0 и APPROVE от `nestjs-reviewer`. Сейчас скрипт проверяет память и падает, пока не заданы тесты (BE-01): «зелёной» приёмки нет, значит задач «Сделано» с приёмкой тоже нет.
- **Почему:** один детерминированный критерий готовности, как во frontend (там SH-D02); тестовый стек backend ещё не выбран.

## SH-D03 — Проект содержит только backend (2026-10-05)
- **Решение:** в памяти одна сторона — `backend/` (ID `BE-`), без `frontend/` и `contracts.md`. Формат с подпапкой стороны сохранён, чтобы протокол `project-memory` работал без изменений. Frontend ведётся в отдельном репозитории `messenger-client-react` (его SH-D04, SH-D09).
- **Почему:** бэкенд — отдельный проект (решение владельца, SH-D09 frontend); заглушки другой стороны вводили бы в заблуждение.
- **Альтернативы:** плоская раскладка без `backend/` (ломает единый протокол скилла); монорепо с двумя сторонами (преждевременно).

## SH-D04 — Решение фиксируется сразу после выбора пользователя; пишет solution-architect (2026-10-05)
- **Решение:** после ответа пользователя на `AskUserQuestion` решение («Решение / Почему / Альтернативы») записывается в `decisions.md`: если варианты готовил `solution-architect` — он сам (основная сессия передаёт выбор через `SendMessage`), иначе основная сессия. Нет выбора — ничего не пишем.
- **Почему:** агенты читают готовые решения и не изобретают их заново; причины фиксируются, пока свежи. Перенос SH-D05 frontend.
- **Альтернативы:** запись после реализации (решения теряют контекст); отдельный вопрос «записывать ли?» (лишний шаг).

## SH-D05 — Жёсткое правило для всех агентов: сомнение или нехватка данных → вопрос пользователю (2026-10-05)

## BE-D05 — Доступ к PostgreSQL: Prisma (2026-10-05)
- **Решение:** Prisma (схема, миграции, клиент). Выбор пользователя; сборка/ESM-интеграция проверяется при реализации.

## SH-D12 — Контракт auth не расширяется полем `isAdmin` (2026-10-05)
- **Решение:** `GET /api/auth/session` остаётся как в контракте клиента (четыре поля `user` + `csrfToken`); эндпоинты `/api/admin/*` доступны только админу, клиент о роли не знает, админ-UI вне фаз 1–4. Выбор пользователя. Расширение (`isAdmin` в теле сессии) отложено — задача BE-06 (техдолг).
- **Почему:** не менять контракт клиента и не требовать правок клиента ради админ-UI, которого пока нет. Пользователь причину отдельно не называл.
- **Альтернативы:** добавить `isAdmin` в тело `session` сейчас (нужна правка клиента) — отложено в BE-06.

## BE-D07 — Отправка сообщений через REST, WebSocket только для доставки (2026-10-05)
- **Решение:** клиент отправляет сообщение `POST /api/chats/:id/messages`; сокет доставляет события (`message.new` и др.) и ничего не принимает от клиента, кроме служебных кадров WebSocket. Прикладного `ping` от клиента нет, живость — серверный WebSocket ping раз в 30 с. Выбор пользователя.
- **Почему:** идемпотентность по `clientId`, валидация, лимиты, CSRF и коды ответов остаются в одном месте; отправка работает при временно оборванном сокете; REST проще тестировать (supertest). Рекомендация принята пользователем после уточнения, что ping — служебный кадр, а не доставка.
- **Альтернативы:** отправка через сокет (`message.send` + `message.ack`: меньше задержка, но протокол ошибок/лимитов дублируется и отправка падает при обрыве сокета); оба способа сразу (YAGNI).

## BE-D15 — Вход по `providerUserId`: привязка allowlist к пользователю, обновление логина/email (2026-10-07) — ЗАМЕНЕНО SH-D14
- **Решение:** после первого входа запись allowlist привязывается к пользователю (`allowlist.user_id`, unique). Логин/email хранится только в `allowlist.provider_login` (в `users` — нет, спека §1 в силе). Пользователь, известный по (`provider`, `provider_user_id`) и привязанный к allowlist (или админ), входит даже при смене логина/email у провайдера; при несовпадении запись allowlist обновляется. Чужой аккаунт (другой `provider_user_id`) со старым логином отклоняется (`not_allowed`): запись привязана к другому пользователю. Распространено на GitHub. Выбор пользователя; колонка `users.provider_login` была добавлена и убрана по его решению (нигде не читалась).
- **Конфликт логина (решение пользователя):** если известный пользователь сменил логин на тот, что в allowlist привязан к другому аккаунту, вход отклоняется и пользователю сообщается, что логин/email занят: редирект `/?auth_error=login_taken` (REST-код `login_taken`, 409). Имя кода `login_taken` подтверждено пользователем (2026-10-07). До клиента доходит только как `auth_error` в редиректе; JSON-409 клиент не получает — в спеке разделить значения `auth_error` и `error.code`. Клиенту нужно добавить сообщение (как для `not_allowed`, SH-D12).
- **Уточнение исполнителя (Ruling):** первый админ из конфигурации (`FIRST_ADMIN`) применяется, только пока в БД нет ни одного администратора; дальше админ определяется по `users.is_admin`, иначе занявший старый логин админа получил бы права. Подтверждено пользователем (2026-10-07). Цена ошибки: при потере единственного админа нужен ручной сброс — процедура (`UPDATE users SET is_admin ...`) описывается в README, CLI-команды нет. Привязка записи allowlist атомарная и идемпотентная для того же пользователя (`updateMany ... OR [userId null, userId тот же]`): чужой аккаунт запись не перехватит, а параллельные первые входы одного аккаунта (две вкладки) не получают ложный `not_allowed` (гонка найдена ревью, закреплена тестом на 20 итераций).
- **Почему:** логин и email у провайдеров меняются, а идентификатор аккаунта — нет; без привязки смена логина либо блокирует человека, либо отдаёт его место другому.

## BE-D20 — Контракт фазы 3 (сообщения): ответы на вопросы системного аналитика (2026-10-08)
- **Решение (выбор пользователя):**
  - `clientId` — только UUID (`z.uuid()`). Повтор с тем же `clientId` и другим `body` возвращает исходное сообщение, `200` (как в спеке).
  - Длина `body` считается в кодовых точках (эмодзи = 1), максимум 4000; после `trim` не пусто (хранится без изменений); `\u0000` → `400 validation_failed`.
  - Лимит 30 сообщений в минуту — в памяти процесса, скользящее окно, без новых библиотек. Ограничение: сбрасывается при рестарте, не масштабируется горизонтально (SH-D06).
  - `GET /chats/:id/messages` — голый массив `ChatMessageDto` по возрастанию `seq`; `before`/`since` исключающие, `limit` по умолчанию 50, максимум 100 (и для `since`), оба курсора сразу → `400`. `POST /chats/:id/read`: `seq > last_seq` → `400`; `seq ≤ last_read_seq` → `204` без изменений.
- **Рекомендации аналитика, не подтверждённые отдельно (принять или поправить при плане):** повтор проверяет членство, но не считается в лимит; членство (404) проверяется раньше лимита (429); `POST` возвращает `ChatMessageDto` (201 новое / 200 повтор); порт `ChatEventsPublisher` расширяется событием `message.new` (без публикации при повторе); отдельный модуль messages; конфиг `MAX_MESSAGE_LENGTH=4000`, `MESSAGE_RATE_PER_MINUTE=30`; идемпотентность — блокировка чата (`requireMember lock`) → `SELECT` по `(chat_id, sender_id, client_id)` → `UPDATE last_seq` + `INSERT` (P2002 внутри транзакции PG невозможно обработать).
- **Почему:** снимает пробелы контракта и 500 от aborted-транзакции до плана BE-08, без новых библиотек.
- **Альтернативы (не выбраны):** `clientId` как nanoid-строка 1..64; 409 при повторе с другим body; UTF-16 длина; `@nestjs/throttler`; подсчёт лимита по БД; `{messages, hasMore}`; обрезка `seq` в `read`.

## BE-D21 — Контракт фазы 4 (WebSocket): ответы на вопросы системного аналитика (2026-10-08)
- **Решение (выбор пользователя):**
  - Эндпоинт `/ws`. Порядок проверок до апгрейда: путь → `Origin` → сессия. `Origin` сравнивается в нормализованном виде (`new URL(o).origin`) со списком `ALLOWED_ORIGINS`; отсутствующий `Origin` → `403`, нет/истекла сессия → `401`.
  - Сессия закончилась (logout, повторный вход, истечение): сокет закрывается кодом `4401` на тике heartbeat (раз в 30 с: проверка `expiresAt` и один батч-запрос по `sessions`). Удаление из allowlist сокет не закрывает (BE-D17).
  - Лимит сокетов на пользователя — `WS_MAX_SOCKETS_PER_USER`, по умолчанию 10; при превышении самый старый закрывается кодом `4008`.
  - Прикладной кадр от клиента → кадр `error` с кодом `unsupported_type`, соединение остаётся; `maxPayload` ~4 КиБ (больший кадр ws закрывает сам кодом 1009).
  - Медленный клиент: `terminate()` при `bufferedAmount` > 1 МиБ (клиент догоняет через REST `since`).
  - Коды закрытия: `4401` сессия кончилась, `4008` вытеснен, `1001` shutdown; без pong — `terminate()` (клиент видит 1006). Клиенту: 1006 до `open` → `GET /api/auth/session` (401 → экран входа, иначе реконнект с backoff и догонкой `since`); в dev-прокси клиента нужен `/ws` с `ws: true`.
  - Зависимости: `@nestjs/platform-ws` и `@nestjs/websockets` ^12, `ws` (явно), `@types/ws` (dev); клиент `ws` в e2e. Решение BE-D06 не меняется.
- **Рекомендации аналитика, не подтверждённые отдельно (принять или поправить при плане):** разбор cookie выносится в `SessionsService.authenticate(cookieHeader)` (его используют `SessionGuard`, `AuthController` и WS); собственный `SessionWsAdapter extends WsAdapter` с `verifyClient`; `WsChatEvents` привязывается к `CHAT_EVENTS` через `useExisting`, `publish` не бросает (try/catch на `send`, `readyState`, один `JSON.stringify`, без `recipients` в кадре, дедупликация получателей); конфиг `WS_HEARTBEAT_MS` (по умолчанию 30000); порядок `message.new`/`chat.*` между транзакциями не гарантируется — правила для клиента в спеке (неизвестный чат → `GET /chats/:id`, разрыв `seq` → `since`, `message.new` после `chat.removed` игнорировать); формулировку спеки про «получатели в момент рассылки» поправить (снимок в транзакции).
- **Почему:** закрывает пробелы §3 спеки (CSWSH, жизненный цикл сокета, лимиты) до плана BE-09 без новых решений по стеку.
- **Альтернативы (не выбраны):** без gateway на `ws` + `upgrade` (отход от BE-D06); мгновенное закрытие через хук в `SessionsService.destroy`; не закрывать сокет после окончания сессии; отклонение рукопожатия по лимиту (429); пропуск запросов без `Origin`; путь `/api/ws`; закрытие соединения при прикладном кадре.

## BE-D22 — Слишком большое тело запроса: `413 validation_failed` (2026-10-09)
- **Решение (выбор пользователя):** тело запроса больше лимита body-parser (~100 КБ) отдаёт `413` с `error.code = validation_failed`; нового кода в контракте нет. Любая клиентская ошибка body-parser (`status` 4xx без `HttpException`) отдаётся с её статусом и `validation_failed` (`AppExceptionFilter`). Ранее отдавалось `500 internal_error`.
- **Почему:** ошибка клиента должна быть 4xx; клиент обрабатывает её как обычную ошибку валидации.
- **Альтернативы (не выбраны):** `413 payload_too_large` (новый код в контракте); `400 validation_failed`.

## BE-D23 — Вопросы клиента BE-17: `seq` без пропусков, `hasMore`, история, запасное имя (2026-10-09) — ЧАСТИЧНО ЗАМЕНЕНО BE-D28, SH-D14
- **Решение (выбор пользователя):**
  - `seq` в чате идёт с 1 без пропусков — закреплено контрактом (инкремент `last_seq` и вставка в одной транзакции под `FOR UPDATE` чата; откат возвращает счётчик). Гарантия относится к выдаче номеров, не к наличию сообщений в истории.
  - `GET /chats/:id/messages` отдаёт `{ messages: ChatMessageDto[], hasMore: boolean }` (было: голый массив; отменяет «Альтернативы» BE-D20). `hasMore` — есть ли ещё сообщения за страницей в направлении запроса: для `before`/без курсора — старше первого элемента, для `since` — новее последнего.
  - Новый участник группы видит всю историю до вступления (как сейчас, без `first_seq`).
  - Пустое `name`/`given_name` Google и пустое `name` GitHub → запасное значение (`FALLBACK_NAME` / `login`); `name` не бывает пустым.
  - Rate limit на вход не добавляется (для закрытой группы не нужен) — зафиксировано в спеке.
  - `lastReadSeq` в составе участников и событие о чтении — отдельной задачей (BE-20), решения нет.
- **Почему:** клиенту нужен однозначный признак конца истории/догонки вместо эвристики «пришло меньше `limit`»; клиент ещё не подключён к реальным сообщениям, поэтому ломающее изменение формы сейчас дешевле, чем позже.
- **Альтернативы (не выбраны):** заголовок `X-Has-More` с телом-массивом; `first_seq` участника для скрытия истории; rate limit на `/api/auth/*`; реализация `lastReadSeq` и `chat.read` в этой задаче.

## SH-D14 — Доступ: инвайт-ссылки от админа и вход по passkeys вместо OAuth и allowlist (2026-10-09)
- **Решение (выбор пользователя):** вход через Google/GitHub OAuth убирается полностью. Новые участники попадают в группу только по одноразовой инвайт-ссылке, которую выпускает админ (без SMTP и email); вход — passkeys (WebAuthn). Реальных пользователей и данных в БД нет, поэтому схема чистится одной миграцией, без expand→contract. Заменяет SH-D09 (allowlist по аккаунту провайдера) и SH-D10 в части «первый админ из конфигурации» (bootstrap — BE-D26); управление участниками через `/api/admin/*` сохраняется. Делает неактуальными BE-D10 (arctic), BE-D11 (email Google в allowlist), BE-D12 (имя из профиля Google), BE-D15 (вход по `providerUserId`, `login_taken`, `FIRST_ADMIN`) и BE-D19 в части сериализации OAuth-входов (сам паттерн advisory lock/атомарного claim остаётся допустимым); пункт BE-D23 про запасное имя Google/GitHub теряет смысл (имя вводит пользователь, BE-D25).
- **Почему:** пользователь не хочет зависеть от Google/GitHub; не у всех участников есть такие аккаунты. Стоимость OAuth причиной не является (первоначальное предположение «платно» неверно).
- **Альтернативы (не выбраны):** оставить OAuth и allowlist; вход по паролю или magic-link (требует SMTP/email).

## BE-D24 — WebAuthn: `@simplewebauthn/server`, параметры церемоний, хранение challenge (2026-10-09)
- **Решение (выбор пользователя):**
  - Серверная библиотека — `@simplewebauthn/server` (^14, MIT, ESM, Node ≥ 22); новая зависимость согласована. Клиентскую сторону (нативные `parseCreationOptionsFromJSON`/`toJSON()` или `@simplewebauthn/browser`) выбирает клиент; сервер отдаёт `*OptionsJSON` и принимает `RegistrationResponseJSON`/`AuthenticationResponseJSON`.

  - Challenge — таблица в БД, TTL 5 минут; в HttpOnly cookie церемонии хранится только её id; погашение одним `DELETE … RETURNING` (одноразовость атомарна).

- **Рекомендации архитектора, не подтверждённые отдельно (принять или поправить при плане):** WebAuthn user handle — отдельная колонка `users.webauthn_user_id` (случайные 32 байта, unique), а не байты `users.id`; cookie церемонии с `path=/api/auth`; ошибка неудачной церемонии — `401 auth_failed`; e2e — программный аутентификатор в тестовой поддержке (ES256 через `node:crypto`) вместо поддельного OAuth-провайдера. Эскиз контракта (пути `/api/auth/passkey/{register,login}/{options,verify}`, `/api/me/passkeys`, `/api/admin/invites`) — ориентир, финал определяет план реализации.
- **Почему:** самая распространённая и поддерживаемая библиотека с высокоуровневым API и встроенной проверкой UV/счётчика; passkey — единственный фактор входа, поэтому UV обязателен; discoverable credentials не требуют ввода логина и работают с синхронизацией и кросс-девайс (гибридный QR) без доработок сервера; challenge в БД переживает рестарт и повторяет паттерн одноразовой cookie `oauth_state`.
- **Альтернативы (не выбраны):** `fido2-lib` (свежий мажор 4.0, низкоуровневый API), `@passwordless-id/webauthn` (меньше сообщество и аудит), своя реализация (риск ошибок проверки); `userVerification: 'preferred'`; challenge в памяти процесса (теряется при рестарте) или в подписанной cookie (новый секрет, повтор в пределах TTL).

## BE-D25 — Инвайты, восстановление доступа и добавление passkey (2026-10-09)
- **Решение (выбор пользователя):**
  - Инвайт: токен 32 байта (`randomBytes`, base64url), в БД хранится SHA-256; ссылка `PUBLIC_URL/invite#<token>` (токен во фрагменте, клиент передаёт его в теле POST); TTL `INVITE_TTL_HOURS=72`; одноразовый; админ может отозвать. Погашение атомарное — условный `UPDATE` (не использован, не отозван, не истёк) в одной транзакции с созданием пользователя и passkey.
  - Админ при создании инвайта ничего не задаёт: имя вводит пользователь при регистрации; повышение до админа — отдельным действием админа.
  - Восстановление и новое устройство без доступа к старому: админ выпускает ссылку восстановления (`invites`, `kind = recovery`, привязана к существующему пользователю); при погашении к пользователю добавляется новый passkey, все его сессии отзываются, старые passkeys остаются.
  - Добавление ещё одного passkey из активной сессии разрешено, только если сессия младше 10 минут (нужен `sessions.created_at`, BE-D29).
- **Почему:** токен с хешем в БД — тот же подход, что у сессий; фрагмент не попадает в логи прокси и `Referer`; ограничение по возрасту сессии не даёт украденной cookie превратиться в постоянный доступ через новый passkey.
- **Альтернативы (не выбраны):** TTL 24 ч или 7 дней; имя или флаг админа в инвайте; recovery-коды; при восстановлении отзывать и passkeys или ничего не отзывать; step-up свежим assertion или добавление passkey без ограничений.

## BE-D26 — Bootstrap и восстановление админа: CLI `npm run admin:invite` (2026-10-09)
- **Решение (выбор пользователя):** первый админ и восстановление потерянного админа — CLI-командой `npm run admin:invite` на сервере: она выпускает одноразовую ссылку (инвайт с правами админа или ссылку восстановления для существующего админа). Переменная `FIRST_ADMIN` удаляется. Заменяет SH-D10 в части bootstrap и «Уточнение исполнителя» BE-D15 (`FIRST_ADMIN`, ручной `UPDATE users SET is_admin` в README).
- **Почему:** нужен shell-доступ к серверу, секрет не лежит в env и не попадает в логи; та же команда закрывает отсутствующую процедуру восстановления админа.
- **Альтернативы (не выбраны):** токен в лог при старте, пока нет админов (логи могут храниться и пересылаться); `BOOTSTRAP_TOKEN` в env (секрет остаётся в env, не помогает при потере админа).

## BE-D27 — Отключение пользователя: `users.disabled_at` вместо удаления из allowlist (2026-10-09)
- **Решение (выбор пользователя):** таблица `allowlist` удаляется; доступ отзывается установкой `users.disabled_at`: отзыв всех сессий пользователя, запрет входа, скрытие пользователя так же, как раньше через `allowedUserWhere` (файл удалён в BE-21; правило — `activeUserWhere` в `src/users/active-user.ts`).
- **Почему:** при инвайтах «есть пользователь» означает «допущен», отдельный список не нужен; поведение для остальных участников сохраняется.
- **Альтернативы (не выбраны):** полное удаление пользователя; пока без отключения.

## BE-D28 — Rate limit на публичные эндпоинты входа и инвайтов; `trust proxy` (2026-10-09)
- **Решение (выбор пользователя):** существующий `MessageRateLimiter` обобщается в лимитер скользящего окна по ключу; для публичных эндпоинтов (options/verify регистрации и входа, проверка/погашение инвайта) ключ — IP клиента, порядка 20 запросов в минуту; ключи периодически вычищаются (сейчас Map не очищается). В проде один reverse proxy: `trust proxy` на 1 hop, задаётся через env. Заменяет пункт BE-D23 «rate limit на вход не добавляется».
- **Почему:** публичные эндпоинты пишут challenge в БД и проверяют подписи — вектор DoS; переиспользование готового лимитера без новых зависимостей; без `trust proxy` за прокси все запросы имели бы один IP.
- **Альтернативы (не выбраны):** без лимита, только TTL challenge; `@nestjs/throttler` (новая зависимость, уже отклонён в BE-D20).

## BE-D29 — Сессии: 7 дней абсолютно, `created_at`, отзыв всех сессий пользователя (2026-10-09)
- **Решение (выбор пользователя):** срок сессии остаётся 7 дней абсолютно, idle-таймаута нет; в `sessions` добавляется `created_at`; `SessionsService` получает отзыв всех сессий пользователя (используется при восстановлении — BE-D25 и отключении — BE-D27). Открытые сокеты закрываются кодом `4401` на тике heartbeat (BE-D21).
- **Почему:** повторный вход по passkey дешёв, idle-таймаут потребовал бы записи на каждый запрос; `created_at` нужен для правила «сессия младше 10 минут» (BE-D25).
- **Альтернативы (не выбраны):** idle-таймаут.

## BE-D30 — План BE-21 (passkeys и инвайты): ответы на вопросы проверки плана (2026-10-09)
- **Решение (выбор пользователя, план `docs/superpowers/plans/2026-10-09-passkeys-invites.md`):**
  - Неудачная WebAuthn-церемония — `401 auth_failed` везде, включая `/api/me/passkeys`. Клиентское правило меняется: выход из системы только при `401 unauthorized`.
  - `TRUST_PROXY` по умолчанию `0`; при https в `PUBLIC_URL` и значении `0` — предупреждение в лог при старте (уточняет BE-D28).
  - Ссылка восстановления создаётся через `POST /api/admin/invites {kind: 'recovery', userId}` — один ресурс, без цикла модулей; отдельного `/api/admin/users/:id/recovery` нет.
  - Админка пользователей: `GET /api/admin/users`, `PATCH /api/admin/users/:id {isAdmin?, disabled?}`; изменить себя админ не может → `403 forbidden`.
  - Имя пользователя: после `trim` 1–64 символа.
  - Имя passkey (`passkeyName`, 1–64) клиент передаёт обязательно при каждом создании ключа; без него `400 validation_failed`.
  - `RP_NAME` по умолчанию `Messenger`.
  - Принято как в плане: коды `invite_invalid` 404, `auth_failed` 401, `user_disabled` 403, `reauth_required` 403, `last_passkey` 409; удаляются `not_allowed`, `login_taken`, `already_exists`. `register/verify` → `201`, `login/verify` → `200`; `register/verify` без токена (инвайт берётся из церемонии); `POST /api/invites/inspect`; у новых пользователей `avatarUrl = ''`; проверка `credProps` не делается; DTO новых ответов в check-sync не сверяются.
  - Приняты рекомендации BE-D24, ранее не подтверждённые отдельно: `users.webauthn_user_id` (32 случайных байта); программный аутентификатор для e2e; cookie церемонии с `path=/api` (отклонение от `/api/auth`: её читает и `/api/me/passkeys`).
- **Технические правки по замечаниям system-analyst (не выбор пользователя):** при входе `userHandle` обязателен; явный `expectedRPID` в обеих проверках; `FOR UPDATE` строки пользователя и создание сессии в той же транзакции (гонка отключения и входа); `SessionsService.find` не возвращает сессии отключённых пользователей; проверка занятости credential id до вставки; `AUTH_RATE_PER_MINUTE=10000` в e2e.
- **Почему:** единый код ошибки церемонии отделяет её от потери сессии; безопасный дефолт `TRUST_PROXY` без доверия к чужим заголовкам с подсказкой в логе для прода; один ресурс инвайтов проще контракта и модульной структуры; запрет менять себя исключает случайную потерю своих прав админом; обязательное имя ключа делает список passkeys различимым.
- **Альтернативы (не выбраны):** `400` для неудачной церемонии везде или смешанно; `TRUST_PROXY` по умолчанию `1` или обязательный; отдельный эндпоинт восстановления; запрет только на снятие последнего админа; имя пользователя 1–100; имя passkey по умолчанию `Passkey` или из типа устройства и даты; обязательный `RP_NAME`.
