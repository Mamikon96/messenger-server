## SH-D01 — AI-память хранится в `.ai/memory/` в репозитории (2026-10-05)
- **Решение:** `CLAUDE.md` в корне + markdown-файлы в `.ai/memory/`; структура перенесена из frontend-проекта `messenger-client-react` (там SH-D01).

## SH-D02 — Приёмка задач через `bash scripts/accept.sh` (2026-10-05)
- **Решение:** задача завершена только при `bash scripts/accept.sh` = 0 и APPROVE от `nestjs-reviewer`. Сейчас скрипт проверяет память и падает, пока не заданы тесты (BE-01): «зелёной» приёмки нет, значит задач «Сделано» с приёмкой тоже нет.
- **Почему:** один детерминированный критерий готовности, как во frontend (там SH-D02); тестовый стек backend ещё не выбран.
- **Альтернативы:** считать приёмкой только проверку памяти (не проверяет код).

## SH-D03 — Проект содержит только backend (2026-10-05)
- **Решение:** в памяти одна сторона — `backend/` (ID `BE-`), без `frontend/` и `contracts.md`. Формат с подпапкой стороны сохранён, чтобы протокол `project-memory` работал без изменений. Frontend ведётся в отдельном репозитории `messenger-client-react` (его SH-D04, SH-D09).
- **Почему:** бэкенд — отдельный проект (решение владельца, SH-D09 frontend); заглушки другой стороны вводили бы в заблуждение.
- **Альтернативы:** плоская раскладка без `backend/` (ломает единый протокол скилла); монорепо с двумя сторонами (преждевременно).

## SH-D04 — Решение фиксируется сразу после выбора пользователя; пишет solution-architect (2026-10-05)
- **Решение:** после ответа пользователя на `AskUserQuestion` решение («Решение / Почему / Альтернативы») записывается в `decisions.md`: если варианты готовил `solution-architect` — он сам (основная сессия передаёт выбор через `SendMessage`), иначе основная сессия. Нет выбора — ничего не пишем.
- **Почему:** агенты читают готовые решения и не изобретают их заново; причины фиксируются, пока свежи. Перенос SH-D05 frontend.
- **Альтернативы:** запись после реализации (решения теряют контекст); отдельный вопрос «записывать ли?» (лишний шаг).

## SH-D05 — Жёсткое правило для всех агентов: сомнение или нехватка данных → вопрос пользователю (2026-10-05)
- **Решение:** любой агент при сомнении или нехватке данных спрашивает пользователя и ничего не придумывает. Правило — `.ai/rules/ask-user.md` и п. 6 «Неснимаемых правил» `CLAUDE.md`. Агент без `AskUserQuestion` возвращает вопросы вызывающему. Перенос SH-D06 frontend.

- **Альтернативы:** правило только в `CLAUDE.md` (агенты вне проекта его не увидят); допущения «по умолчанию» (строят работу на выдумке).

## BE-D05 — Доступ к PostgreSQL: Prisma (2026-10-05)
- **Решение:** Prisma (схема, миграции, клиент). Выбор пользователя; сборка/ESM-интеграция проверяется при реализации.

## BE-D06 — WebSocket: нативный `ws` через `@nestjs/platform-ws` (2026-10-05)

## SH-D12 — Контракт auth не расширяется полем `isAdmin` (2026-10-05)
- **Решение:** `GET /api/auth/session` остаётся как в контракте клиента (четыре поля `user` + `csrfToken`); эндпоинты `/api/admin/*` доступны только админу, клиент о роли не знает, админ-UI вне фаз 1–4. Выбор пользователя. Расширение (`isAdmin` в теле сессии) отложено — задача BE-06 (техдолг).
- **Почему:** не менять контракт клиента и не требовать правок клиента ради админ-UI, которого пока нет. Пользователь причину отдельно не называл.
- **Альтернативы:** добавить `isAdmin` в тело `session` сейчас (нужна правка клиента) — отложено в BE-06.

## BE-D07 — Отправка сообщений через REST, WebSocket только для доставки (2026-10-05)
- **Решение:** клиент отправляет сообщение `POST /api/chats/:id/messages`; сокет доставляет события (`message.new` и др.) и ничего не принимает от клиента, кроме служебных кадров WebSocket. Прикладного `ping` от клиента нет, живость — серверный WebSocket ping раз в 30 с. Выбор пользователя.
- **Почему:** идемпотентность по `clientId`, валидация, лимиты, CSRF и коды ответов остаются в одном месте; отправка работает при временно оборванном сокете; REST проще тестировать (supertest). Рекомендация принята пользователем после уточнения, что ping — служебный кадр, а не доставка.
- **Альтернативы:** отправка через сокет (`message.send` + `message.ack`: меньше задержка, но протокол ошибок/лимитов дублируется и отправка падает при обрыве сокета); оба способа сразу (YAGNI).

## BE-D15 — Вход по `providerUserId`: привязка allowlist к пользователю, обновление логина/email (2026-10-07)
- **Решение:** после первого входа запись allowlist привязывается к пользователю (`allowlist.user_id`, unique). Логин/email хранится только в `allowlist.provider_login` (в `users` — нет, спека §1 в силе). Пользователь, известный по (`provider`, `provider_user_id`) и привязанный к allowlist (или админ), входит даже при смене логина/email у провайдера; при несовпадении запись allowlist обновляется. Чужой аккаунт (другой `provider_user_id`) со старым логином отклоняется (`not_allowed`): запись привязана к другому пользователю. Распространено на GitHub. Выбор пользователя; колонка `users.provider_login` была добавлена и убрана по его решению (нигде не читалась).
- **Конфликт логина (решение пользователя):** если известный пользователь сменил логин на тот, что в allowlist привязан к другому аккаунту, вход отклоняется и пользователю сообщается, что логин/email занят: редирект `/?auth_error=login_taken` (REST-код `login_taken`, 409). Имя кода `login_taken` подтверждено пользователем (2026-10-07). До клиента доходит только как `auth_error` в редиректе; JSON-409 клиент не получает — в спеке разделить значения `auth_error` и `error.code`. Клиенту нужно добавить сообщение (как для `not_allowed`, SH-D12).
- **Уточнение исполнителя (Ruling):** первый админ из конфигурации (`FIRST_ADMIN`) применяется, только пока в БД нет ни одного администратора; дальше админ определяется по `users.is_admin`, иначе занявший старый логин админа получил бы права. Подтверждено пользователем (2026-10-07). Цена ошибки: при потере единственного админа нужен ручной сброс — процедура (`UPDATE users SET is_admin ...`) описывается в README, CLI-команды нет. Привязка записи allowlist атомарная и идемпотентная для того же пользователя (`updateMany ... OR [userId null, userId тот же]`): чужой аккаунт запись не перехватит, а параллельные первые входы одного аккаунта (две вкладки) не получают ложный `not_allowed` (гонка найдена ревью, закреплена тестом на 20 итераций).
- **Почему:** логин и email у провайдеров меняются, а идентификатор аккаунта — нет; без привязки смена логина либо блокирует человека, либо отдаёт его место другому.
- **Альтернативы:** отклонять вход до правки allowlist админом; хранить логин в `users` — не выбраны.
- **Код `already_exists` (2026-10-07, выбор пользователя):** дубль записи в allowlist (`POST /api/admin/allowlist`) → `409` с кодом `already_exists`; код общий, пригоден для других дублей. Альтернативы (`conflict`, только статус без кода) не выбраны.

## SH-D13 — К исследованию и планированию подключается system-analyst (2026-10-07)
- **Решение:** на стадии исследования и планирования задач разработки основная сессия запускает `system-analyst` (до плана и, при выборе технологии, до `solution-architect`); его находки и вопросы учитываются в плане и передаются пользователю. Правило — `.ai/rules/research-planning.md`. Не требуется для правок конфигов/процесса/документации и багфиксов без смены контракта и схемы.
- **Почему:** анализ 2026-10-07 нашёл расхождения спеки и контракта (BE-12), которые дешевле ловить до реализации: дубли, несогласованность API, лишние обращения к БД, риски масштабирования.

## BE-D16 — Контракт фазы 2 (чаты): ответы на вопросы системного аналитика (2026-10-07)
- **Решение (выбор пользователя):**
  - Пользователь вне allowlist: скрыт из `GET /users`, с ним нельзя создавать чаты и добавлять его в группы; старые чаты и история остаются. `userId` несуществующего или такого пользователя → `404 not_found`.
  - Новый чат: приглашённым уходит событие `chat.created` (симметрично `chat.removed`), данные фиксируются уже в фазе 2.
  - Код `not_a_member` удаляется из списка кодов: не-участник получает `404 not_found`.
  - Роли: один `owner` (создатель); единственный owner не может выйти (`403 forbidden`); передача роли — отдельной задачей позже.
  - Новый код `forbidden` (403 по правам: не админ, не owner); `not_allowed` остаётся только для аккаунта вне allowlist (меняется `AdminGuard`).
  - Direct-чат: `POST /chats/:id/members` и выход запрещены (`400 validation_failed`), состав неизменен. Чат 1:1 с самим собой разрешён.
  - Группа: `memberIds` непустой (создатель — owner, в `memberIds` не входит), `title` 1..100 (длина — предложение исполнителя, пользователь выбрал вариант целиком), `PATCH /chats/:id` (title) только для owner → событие `chat.updated`. Лимит 100 участников → `400 validation_failed`.
  - `GET /chats`: по последней активности, без пагинации; `lastMessage` — полное сообщение, как в `message.new`; собственные сообщения не считаются непрочитанными (отправка сдвигает `last_read_seq` отправителя).
  - WS-кадр ошибки: `{type:"error", payload:{code, message}}`; поправить §4 спеки.
  - Развёртывание: reverse proxy, SPA и `/api` на одном origin; `PUBLIC_URL` — внешний адрес.
- **Почему:** закрывает пробелы спеки до плана BE-07 (раздел C анализа), не плодит коды и сохраняет единый контракт REST/WS.
- **Альтернативы (не выбраны):** отдельные коды `last_owner`/`member_limit`, пометка «неактивен» вместо скрытия, передача роли owner в фазе 2, пагинация `GET /chats`, раздача SPA из NestJS.

## BE-D17 — Дизайн фазы 2 (чаты): ответы на вопросы аналитика (2026-10-07)
- **Решение (выбор пользователя):**
  - «В allowlist» = привязанная запись allowlist ИЛИ `users.is_admin` — один предикат для `GET /users`, создания чата и добавления участника. Вызывающий с живой сессией, удалённый из allowlist, не проверяется (сессии не обрываются по спеке).
  - `GET /chats`: у direct-чата поле `peer {id, name, avatarUrl}`; сортировка по последней активности, у чата без сообщений — `chats.created_at`.
  - Единый `ChatDto = {id, type, title, lastSeq, members:[{userId, name, avatarUrl, role}]}` — тело `GET /chats/:id`, `POST /chats`, `PATCH /chats/:id` и payload `chat.created`; в direct оба участника `member`.
  - `last_read_seq` нового участника группы = `last_seq` на момент добавления.
  - `POST /chats` direct с пользователем вне allowlist → `404`, даже если чат уже есть; `memberIds` с создателем или дублями → `400 validation_failed`.
  - События `chat.*`: порт `ChatEventsPublisher` (интерфейс + DI-токен) с no-op реализацией, вызов после коммита с явными получателями (у `chat.removed` получатель уже не в `chat_members`).
  - Миграция фазы 2: только CHECK типа чата (`direct` ⇔ `direct_key` задан и `title` null; `group` ⇒ `title` задан). Индекс «owner ровно один» не вводится.
- **Исполнительные уточнения (по анализу):** лимит 100 — блокировка строки чата (`SELECT ... FOR UPDATE`) в транзакции; идемпотентный 1:1 — `INSERT ... ON CONFLICT (direct_key) DO NOTHING RETURNING`; чат с собой — ключ `a:a` и одна строка участника; `unreadCount = chats.last_seq − chat_members.last_read_seq`; лимит участников из конфигурации (`MAX_GROUP_MEMBERS`); умолчание фильтра для голого 403 — `forbidden`.
- **Почему:** снимает пробелы контракта и гонки до плана BE-07 без новых библиотек.
- **Альтернативы (не выбраны):** привязка админа к allowlist при входе, полный `members` в `GET /chats`, `last_read_seq = 0`, `@nestjs/event-emitter`, индекс «owner один».

## BE-D18 — Уточнения фазы 2 по итогам ревью задач (2026-10-07)
- **Решение (выбор пользователя):**
  - `chat.updated` (переименование, изменение состава) получают все участники чата, включая инициатора: ответы на добавление/удаление участника — `204` без тела, другим вкладкам инициатора нужен свежий состав. При выходе/удалении удалённый получает `chat.removed`.
  - Чат с собой (direct с собственным `userId`) проходит ту же проверку allowlist, что и любая цель: вызывающий вне allowlist с живой сессией получает `404 not_found`.
  - `pg` объявляется в `devDependencies` (тест подсчёта SQL-запросов в `test/chats.e2e-spec.ts` использует `pg.Client.prototype.query`; раньше — неявная транзитивная зависимость `@prisma/adapter-pg`).
- **Почему:** одно правило получателей; единая проверка allowlist; явная зависимость вместо хрупкой транзитивной.
- **Альтернативы (не выбраны):** исключать инициатора из `chat.updated`; пропускать проверку allowlist для своего id; `PrismaClient` с `$on('query')` без `pg`.

## BE-D19 — Сериализация входов одного аккаунта: `pg_advisory_xact_lock` (BE-13, уточнение BE-D15, 2026-10-07)
- **Решение (выбор пользователя):** первым оператором транзакции `AuthService.signIn` берётся `pg_advisory_xact_lock(hashtextextended('auth:<provider>:<providerUserId>', 0))`: параллельные входы одного аккаунта (несколько вкладок) идут строго по очереди; разные аккаунты друг друга не ждут, их гонку за одну запись allowlist по-прежнему решает атомарный `claim`. Семантика BE-D15 не менялась.
- **Почему:** под READ COMMITTED вкладки одного аккаунта читали разные снимки: у проигравших `allowlistEntry.delete` падал необработанным P2025 (HTTP 500), а у нового аккаунта возникал ложный `not_allowed`. `SELECT … FOR UPDATE` не подходит (у нового аккаунта нет строки для блокировки), `deleteMany` убрал бы только P2025. Подтверждено серией: 20 из 20 прогонов гонок, e2e 93/93.
- **Альтернативы (не выбраны):** ловить P2025/P2002 и повторять транзакцию; `deleteMany` вместо `delete`.
