# Чаты и сообщения

## SH-D11 — Чаты: 1:1 и группы, роли в группе owner/member (2026-10-05)
- **Решение:** ядро поддерживает личные (1:1) и групповые чаты; группу создаёт любой участник и становится её `owner` (управляет составом), остальные — `member`. Роль в чате не связана с ролью администратора системы (SH-D10). Выбор пользователя.
- **Почему:** покрывает «малую группу» из цели проекта (SH-D06) с минимумом ролей. Пользователь причину отдельно не называл.
- **Альтернативы:** группы без ролей (любой управляет составом); только 1:1 — не выбраны.

## BE-D16 — Контракт фазы 2 (чаты): ответы на вопросы системного аналитика (2026-10-07)
- **Решение (выбор пользователя):**
  - Пользователь вне allowlist: скрыт из `GET /users`, с ним нельзя создавать чаты и добавлять его в группы; старые чаты и история остаются. `userId` несуществующего или такого пользователя → `404 not_found`.
  - Новый чат: приглашённым уходит событие `chat.created` (симметрично `chat.removed`), данные фиксируются уже в фазе 2.
  - Код `not_a_member` удаляется из списка кодов: не-участник получает `404 not_found`.
  - Роли: один `owner` (создатель); единственный owner не может выйти (`403 forbidden`); передача роли — отдельной задачей позже.
  - Новый код `forbidden` (403 по правам: не админ, не owner); `not_allowed` остаётся только для аккаунта вне allowlist (меняется `AdminGuard`).
  - Direct-чат: `POST /chats/:id/members` и выход запрещены (`400 validation_failed`), состав неизменен. Чат 1:1 с самим собой разрешён.
  - Группа: `memberIds` непустой (создатель — owner, в `memberIds` не входит), `title` 1..100 (длина — предложение исполнителя, пользователь выбрал вариант целиком), `PATCH /chats/:id` (title) только для owner → событие `chat.updated`. Лимит 100 участников → `400 validation_failed`.
  - `GET /chats`: по последней активности, без пагинации; `lastMessage` — полное сообщение, как в `message.new`; собственные сообщения не считаются непрочитанными (отправка сдвигает `last_read_seq` отправителя).
  - WS-кадр ошибки: `{type:"error", payload:{code, message}}`; поправить §4 спеки.
  - Развёртывание: reverse proxy, SPA и `/api` на одном origin; `PUBLIC_URL` — внешний адрес.
- **Почему:** закрывает пробелы спеки до плана BE-07 (раздел C анализа), не плодит коды и сохраняет единый контракт REST/WS.
- **Альтернативы (не выбраны):** отдельные коды `last_owner`/`member_limit`, пометка «неактивен» вместо скрытия, передача роли owner в фазе 2, пагинация `GET /chats`, раздача SPA из NestJS.

## BE-D17 — Дизайн фазы 2 (чаты): ответы на вопросы аналитика (2026-10-07)
- **Решение (выбор пользователя):**
  - «В allowlist» = привязанная запись allowlist ИЛИ `users.is_admin` — один предикат для `GET /users`, создания чата и добавления участника. Вызывающий с живой сессией, удалённый из allowlist, не проверяется (сессии не обрываются по спеке).
  - `GET /chats`: у direct-чата поле `peer {id, name, avatarUrl}`; сортировка по последней активности, у чата без сообщений — `chats.created_at`.
  - Единый `ChatDto = {id, type, title, lastSeq, members:[{userId, name, avatarUrl, role}]}` — тело `GET /chats/:id`, `POST /chats`, `PATCH /chats/:id` и payload `chat.created`; в direct оба участника `member`.
  - `last_read_seq` нового участника группы = `last_seq` на момент добавления.
  - `POST /chats` direct с пользователем вне allowlist → `404`, даже если чат уже есть; `memberIds` с создателем или дублями → `400 validation_failed`.
  - События `chat.*`: порт `ChatEventsPublisher` (интерфейс + DI-токен) с no-op реализацией, вызов после коммита с явными получателями (у `chat.removed` получатель уже не в `chat_members`).
  - Миграция фазы 2: только CHECK типа чата (`direct` ⇔ `direct_key` задан и `title` null; `group` ⇒ `title` задан). Индекс «owner ровно один» не вводится.
- **Исполнительные уточнения (по анализу):** лимит 100 — блокировка строки чата (`SELECT ... FOR UPDATE`) в транзакции; идемпотентный 1:1 — `INSERT ... ON CONFLICT (direct_key) DO NOTHING RETURNING`; чат с собой — ключ `a:a` и одна строка участника; `unreadCount = chats.last_seq − chat_members.last_read_seq`; лимит участников из конфигурации (`MAX_GROUP_MEMBERS`); умолчание фильтра для голого 403 — `forbidden`.
- **Почему:** снимает пробелы контракта и гонки до плана BE-07 без новых библиотек.
- **Альтернативы (не выбраны):** привязка админа к allowlist при входе, полный `members` в `GET /chats`, `last_read_seq = 0`, `@nestjs/event-emitter`, индекс «owner один».

## BE-D18 — Уточнения фазы 2 по итогам ревью задач (2026-10-07)
- **Решение (выбор пользователя):**
  - `chat.updated` (переименование, изменение состава) получают все участники чата, включая инициатора: ответы на добавление/удаление участника — `204` без тела, другим вкладкам инициатора нужен свежий состав. При выходе/удалении удалённый получает `chat.removed`.
  - Чат с собой (direct с собственным `userId`) проходит ту же проверку allowlist, что и любая цель: вызывающий вне allowlist с живой сессией получает `404 not_found`.
  - `pg` объявляется в `devDependencies` (тест подсчёта SQL-запросов в `test/chats.e2e-spec.ts` использует `pg.Client.prototype.query`; раньше — неявная транзитивная зависимость `@prisma/adapter-pg`).
- **Почему:** одно правило получателей; единая проверка allowlist; явная зависимость вместо хрупкой транзитивной.
- **Альтернативы (не выбраны):** исключать инициатора из `chat.updated`; пропускать проверку allowlist для своего id; `PrismaClient` с `$on('query')` без `pg`.

## BE-D20 — Контракт фазы 3 (сообщения): ответы на вопросы системного аналитика (2026-10-08)
- **Решение (выбор пользователя):**
  - `clientId` — только UUID (`z.uuid()`). Повтор с тем же `clientId` и другим `body` возвращает исходное сообщение, `200` (как в спеке).
  - Длина `body` считается в кодовых точках (эмодзи = 1), максимум 4000; после `trim` не пусто (хранится без изменений); `\u0000` → `400 validation_failed`.
  - Лимит 30 сообщений в минуту — в памяти процесса, скользящее окно, без новых библиотек. Ограничение: сбрасывается при рестарте, не масштабируется горизонтально (SH-D06).
  - `GET /chats/:id/messages` — голый массив `ChatMessageDto` по возрастанию `seq`; `before`/`since` исключающие, `limit` по умолчанию 50, максимум 100 (и для `since`), оба курсора сразу → `400`. `POST /chats/:id/read`: `seq > last_seq` → `400`; `seq ≤ last_read_seq` → `204` без изменений.
- **Рекомендации аналитика, не подтверждённые отдельно (принять или поправить при плане):** повтор проверяет членство, но не считается в лимит; членство (404) проверяется раньше лимита (429); `POST` возвращает `ChatMessageDto` (201 новое / 200 повтор); порт `ChatEventsPublisher` расширяется событием `message.new` (без публикации при повторе); отдельный модуль messages; конфиг `MAX_MESSAGE_LENGTH=4000`, `MESSAGE_RATE_PER_MINUTE=30`; идемпотентность — блокировка чата (`requireMember lock`) → `SELECT` по `(chat_id, sender_id, client_id)` → `UPDATE last_seq` + `INSERT` (P2002 внутри транзакции PG невозможно обработать).
- **Почему:** снимает пробелы контракта и 500 от aborted-транзакции до плана BE-08, без новых библиотек.
- **Альтернативы (не выбраны):** `clientId` как nanoid-строка 1..64; 409 при повторе с другим body; UTF-16 длина; `@nestjs/throttler`; подсчёт лимита по БД; `{messages, hasMore}`; обрезка `seq` в `read`.

## BE-D23 — Вопросы клиента BE-17: `seq` без пропусков, `hasMore`, история, запасное имя (2026-10-09) — ЧАСТИЧНО ЗАМЕНЕНО BE-D28, SH-D14, BE-D33
- **Решение (выбор пользователя):**
  - `seq` в чате идёт с 1 без пропусков — закреплено контрактом (инкремент `last_seq` и вставка в одной транзакции под `FOR UPDATE` чата; откат возвращает счётчик). Гарантия относится к выдаче номеров, не к наличию сообщений в истории.
  - `GET /chats/:id/messages` отдаёт `{ messages: ChatMessageDto[], hasMore: boolean }` (было: голый массив; отменяет «Альтернативы» BE-D20). `hasMore` — есть ли ещё сообщения за страницей в направлении запроса: для `before`/без курсора — старше первого элемента, для `since` — новее последнего.
  - Новый участник группы видит всю историю до вступления (как сейчас, без `first_seq`).
  - Пустое `name`/`given_name` Google и пустое `name` GitHub → запасное значение (`FALLBACK_NAME` / `login`); `name` не бывает пустым.
  - Rate limit на вход не добавляется (для закрытой группы не нужен) — зафиксировано в спеке.
  - `lastReadSeq` в составе участников и событие о чтении — отдельной задачей (BE-20), решения нет.
- **Почему:** клиенту нужен однозначный признак конца истории/догонки вместо эвристики «пришло меньше `limit`»; клиент ещё не подключён к реальным сообщениям, поэтому ломающее изменение формы сейчас дешевле, чем позже.
- **Альтернативы (не выбраны):** заголовок `X-Has-More` с телом-массивом; `first_seq` участника для скрытия истории; rate limit на `/api/auth/*`; реализация `lastReadSeq` и `chat.read` в этой задаче.

## BE-D40 — Допустимые символы во входном тексте: два профиля (2026-10-18)
- **Решение:** один предикат `containsForbiddenChars(value, profile)` в `src/common/text-input.ts`. `singleLine` (`firstName`, `lastName`, `title`, `q`): запрещены весь `\p{Cc}`, U+2028/2029, U+202A–202E, U+2066–2069 и одиночные суррогаты. `multiline` (`body`): запрещены `\p{Cc}` кроме `\t \n \r` и одиночные суррогаты. Эмодзи, RTL, LRM/RLM/ALM разрешены. Проверка по сохраняемому значению (после `trim`). `PATCH /api/me` отдаёт `invalid_format` в `details` с приоритетом `required` > `too_long` > `invalid_format`; чаты и сообщения — `400` без `details`. `login` и пароли не меняются.
- **Почему:** NUL в `firstName`/`title` давал 500 (PostgreSQL), одиночный суррогат молча превращался в U+FFFD; правила были разбросаны по полям.
- **Альтернативы (не выбраны):** глобальный pipe; фильтр ошибки PostgreSQL 22021 → 400; запрет zero-width и noncharacters.
