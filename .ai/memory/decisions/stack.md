# Технологический стек

## SH-D07 — Основа бэкенда: Node.js + WebSocket + PostgreSQL, фреймворк NestJS (2026-10-05)
- **Решение:** Node.js, реалтайм через WebSocket, данные в PostgreSQL (SH-D10 frontend); фреймворк — NestJS (выбор пользователя, BE-D01 ниже). Остальные библиотеки (ORM/драйвер, WebSocket-слой, тестовый стек) — отдельно по `tech-approval.md`.
- **Почему:** контроль и совместимость с контрактом BFF/OAuth из frontend; для ~1 000 пользователей объём невелик.
- **Альтернативы:** BaaS (Supabase/Firebase), Matrix (Synapse), «только клиент на mock-сервере» — отклонены во frontend SH-D10.

## BE-D01 — Фреймворк бэкенда: NestJS (2026-10-05)
- **Решение:** бэкенд на NestJS (Node.js + WebSocket + PostgreSQL по SH-D07). Выбор сделан пользователем при создании структуры памяти.
- **Почему:** пользователь причину не называл (не записываем догадок); при необходимости уточнить.
- **Альтернативы:** Next.js route handlers, Node.js + Fastify/Express — предлагались, не выбраны.

## BE-D03 — Пакетный менеджер: npm (2026-10-05)
- **Решение:** npm (lockfile `package-lock.json`). Выбор пользователя.
- **Почему:** уже установлен, дефолт NestJS CLI, без дополнительной настройки.
- **Альтернативы:** pnpm, yarn — не установлены, пришлось бы ставить; не выбраны.

## BE-D04 — Тестовый стек: Vitest + supertest (заменяет BE-D02) (2026-10-05)
- **Решение:** unit-тесты — Vitest (`*.spec.ts` рядом с кодом), e2e — Vitest + supertest (`test/*.e2e-spec.ts`, `vitest.config.e2e.ts`); конфигурация шаблона Nest CLI 12. Вместе с шаблоном приняты его линтер oxlint и ESM (`"type": "module"`). Выбор пользователя после уточнения.
- **Почему:** актуальный Nest CLI (Nest 12) генерирует проект на Vitest, а не на Jest; посылка BE-D02 («Jest — дефолт CLI») оказалась неверной. Шаблон уже настроен, без ручной правки под ESM.
- **Альтернативы:** Jest + supertest (выбор из BE-D02; требует ручной замены раннера и ts-jest под ESM); `node:test` — не выбраны. BE-D02 и BE-D03 (npm) остаются в силе: BE-D02 отменён этой записью.

## BE-D05 — Доступ к PostgreSQL: Prisma (2026-10-05)
- **Решение:** Prisma (схема, миграции, клиент). Выбор пользователя; сборка/ESM-интеграция проверяется при реализации.
- **Почему:** зрелый тулинг, генерация типизированного клиента и миграций, много примеров с NestJS; пользователь причину отдельно не называл. Известный компромисс: нетривиальные запросы (атомарный `seq` в чате, курсорная пагинация) могут потребовать raw SQL.
- **Альтернативы:** Drizzle ORM (рекомендовался: ближе к SQL, без генератора), TypeORM (проблемы декораторов с esbuild/Vitest и ESM), node-postgres + Kysely (всё вручную) — не выбраны.

## BE-D08 — Тестовая БД: PostgreSQL в Docker Compose (2026-10-07)
- **Решение:** для e2e и интеграционных тестов PostgreSQL поднимается через `docker-compose.yml`; `scripts/accept.sh` стартует контейнер, применяет миграции Prisma и гоняет e2e. Выбор пользователя (рекомендованный вариант).
- **Почему:** реальная БД, как в проде (атомарный `seq`, уникальные индексы, raw SQL); пользователь причину отдельно не называл.
- **Альтернативы:** Testcontainers (доп. зависимость, всё равно нужен Docker), локальный Postgres по `DATABASE_URL` (окружение у каждого своё) — не выбраны.

## BE-D09 — Валидация DTO: zod (2026-10-07)
- **Решение:** входы REST и WebSocket валидируются схемами zod через собственный pipe на границе контроллера. Выбор пользователя (рекомендованный вариант).
- **Почему:** одна схема даёт тип и проверку; нет декораторов, которые плохо дружат с esbuild/Vitest и ESM. Пользователь причину отдельно не называл.
- **Альтернативы:** class-validator + class-transformer (стандартный `ValidationPipe`, но декораторы и метаданные) — не выбран.

## BE-D13 — Логирование: встроенный `Logger` из Nest (2026-10-07)
- **Решение:** ошибки 500 и сбои OAuth-обмена пишутся через `Logger` из `@nestjs/common`, без токенов и секретов. Выбор пользователя.
- **Почему:** без новых зависимостей, достаточно для малой группы.
- **Альтернативы:** pino (`nestjs-pino`) — не выбран.

## BE-D14 — Загрузка `.env`: флаг `--env-file` Node/Nest (2026-10-07)
- **Решение:** `.env` читается встроенными средствами Node (`--env-file`, `process.loadEnvFile`), без `dotenv`. Выбор пользователя.
- **Почему:** Node умеет это сам, зависимость не нужна.
- **Альтернативы:** `dotenv` — не выбран.
