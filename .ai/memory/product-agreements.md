# Соглашения по продукту, архитектуре и бэкенду
Читать: при проектировании контракта API/событий, схемы БД, задач про реалтайм и серверное хранение. Основание: SH-D06, SH-D07 (`decisions.md`). Источник: `product-agreements.md` frontend-проекта `messenger-client-react`; пункты ниже — рекомендации, уточняются в этом проекте.

## Цель и рамки (SH-D06)
- Реальный мессенджер для малой закрытой группы: до ~1 000 пользователей, один сервер.
- Безопасность: TLS на транспорте, сессия по cookie (контракт auth — во frontend `frontend/auth-contract.md`, см. `memory/README.md`), без E2EE.
- Не входит (YAGNI на старте): публичный масштаб и горизонтальное масштабирование, E2EE, федерация, корпоративные SSO/аудит.

## Основа бэкенда (SH-D07)
- Node.js + NestJS + WebSocket + PostgreSQL. Остальные библиотеки — отдельное согласование по `tech-approval.md`.
- Отклонены: BaaS (Supabase/Firebase), Matrix (Synapse), «только клиент на mock-сервере».
- Не выбрано отдельно: SSE+POST как запасной транспорт, ORM/драйвер БД, WebSocket-слой.

## Из чего состоит мессенджер
| Слой | Что входит |
|---|---|
| Ядро | Чаты (1:1, группы), участники и роли, сообщения, история с пагинацией |
| Реалтайм | Доставка новых сообщений, переподключение и догонка пропущенного |
| Состояние | Статусы сообщений, непрочитанные, presence, «печатает» |
| Дополнительно | Медиа и файлы, поиск, ответы, правки и удаление, реакции |
| Платформа | Уведомления (Web Push), безопасность, лимиты, наблюдаемость |

## Проектные соглашения (рекомендации; уточнять при проектировании)
- **Идемпотентность:** клиент генерирует `clientId` сообщения, сервер отвечает идемпотентно; дубли при повторной отправке не создаются.
- **Порядок:** задаёт серверный `seq` внутри чата, не `Date.now()` клиента; время — серверное.
- **Догонка:** клиент хранит последний `seq` по чату и после реконнекта запрашивает `since=seq`.
- **Статусы:** `sending` → `sent` → (`delivered` → `read`) / `failed`, повторная отправка из UI.
- **Непрочитанные:** у участника чата `last_read_seq`; счётчик считается от него.
- **Presence и typing:** эфемерные события, в БД не пишутся, throttle на клиенте и сервере.
- **История:** курсорная пагинация по `seq`, не offset.
- **Медиа:** загрузка в объектное хранилище по presigned URL; проверка типа и размера.

## Безопасность
- WebSocket: аутентификация cookie-сессией, проверка `Origin` (защита от cross-site WebSocket hijacking), проверка членства в чате на **каждом** событии, а не только при подключении.
- CSRF для изменяющих запросов (как в контракте auth); текст сообщений хранится и отдаётся как текст, санитизация ссылок — на клиенте, сервер валидирует вход (XSS).
- Лимиты: размер сообщения, частота отправки, размер файлов.

## Что нужно клиенту от сервера
- Нормализованные сущности и события для стора; `seq` и `since` для догонки.
- Несколько вкладок одного пользователя — несколько сокетов; сервер должен это допускать.
- e2e реалтайма на клиенте требует либо WebSocket в mock-BFF, либо реального тестового бэкенда — второй вариант даёт этот проект.

## Черновая декомпозиция (по фазам; задачи не заведены, кроме BE-01…)
1. Основа: контракт API и событий, схема БД, каркас сервера, auth (OAuth/BFF по контракту frontend).
2. Чаты и участники: создание, участники, список чатов.
3. Сообщения: REST, история с курсорной пагинацией.
4. Реалтайм: WebSocket, `seq`, догонка, статусы.
5. Присутствие: непрочитанные, presence, typing.
6. Улучшения: правка и удаление, ответы, поиск.
7. Медиа и уведомления: файлы, Web Push.
8. Платформа: лимиты, логирование, деплой, e2e.
Задачи заводятся в `tasks.md` по мере проработки; разбиение крупной фазы — через `task-planner` (после его перенастройки на `tasks.md`, BE-05).
