# Спека: вход и регистрация по логину и паролю

> Статус: согласована с пользователем 2026-10-13, **не реализована**. Действующий контракт до реализации — `docs/client-integration.md`; после реализации на бэкенде эта спека вливается в него (§1.3, §2, §3.11, §4, §7) и удаляется.
> Решения: SH-D18 (доступ), BE-D31 (хэш и политика пароля), BE-D32 (сессии), BE-D33 (профиль, логин, имя), BE-D34 (ошибки и лимиты), BE-D35 (уточнения после планирования). Заменяет SH-D14 и всё, что связано с passkeys и инвайтами.

## 1. Что меняется в целом
- Регистрация открытая: любой создаёт аккаунт по логину и паролю, без инвайта.
- Вход — по логину и паролю. Passkeys и инвайты удаляются полностью.
- Сессия живёт, пока пользователь сам не выйдет: скользящий срок 400 дней с продлением при активности.
- В БД хранятся логин и хэш пароля (argon2id).
- Сброса забытого пароля нет (вне рамок MVP). Есть смена пароля и «выйти на всех устройствах».
- Имя пользователя при регистрации генерируется сервером; пользователь меняет его в настройках (имя и фамилия).

Не меняется: cookie-сессия `sid`, CSRF (`X-CSRF-Token`), проверка `Origin` на публичных `POST`, формат ошибок, `GET /api/auth/session`, `POST /api/auth/logout`, правило «выход из системы только при `401 unauthorized`», чаты, сообщения, WebSocket.

## 2. Эндпоинты

### 2.1. `POST /api/auth/register`
Публичный: без сессии и CSRF, требует допустимый `Origin`, под rate limit (§6).
```json
{ "login": "alice", "password": "correct horse battery" }
```
- `201` — тело как у `GET /api/auth/session` (§2.3), ставится cookie `sid`. Пользователь сразу залогинен. Если в браузере уже была сессия, она уничтожается (как при входе).
- `400 validation_failed` + `details` (§5).
- `409 login_taken` — логин занят (сравнение после нормализации, §4.1).
- `403 forbidden` — нет допустимого `Origin`; `429 rate_limited`.

Имя не передаётся: сервер генерирует его (§4.3).

### 2.2. `POST /api/auth/login`
Публичный: без сессии и CSRF, требует допустимый `Origin`, под rate limit (§6).
```json
{ "login": "Alice", "password": "correct horse battery" }
```
- `200` — тело как у `GET /api/auth/session`, ставится cookie `sid`. Прежняя сессия этого браузера уничтожается: её сокеты закроются `4401`, REST с ней получит `401 unauthorized`.
- `401 auth_failed` — логина нет **или** пароль неверный (ответ и время ответа одинаковые).
- `403 user_disabled` — пользователь отключён админом; отдаётся только после верного пароля.
- `400 validation_failed` — пустые поля или неверный тип; формат логина и политика пароля при входе **не** проверяются (только при регистрации и смене пароля).
- `403 forbidden`, `429 rate_limited`.

### 2.3. `GET /api/auth/session`
Без изменений, кроме формы `user` (`SessionUser`, §3):
```json
{
  "user": { "id": "6f1c…", "login": "alice", "firstName": "Сонный", "lastName": "Енот", "name": "Сонный Енот", "avatarUrl": "" },
  "csrfToken": "q3Jm0w1n4cXb2bX7hR8ZpX0kq4k5o9Qe"
}
```
`401 unauthorized` — не авторизован. Вызов продлевает сессию (§7).

### 2.4. `POST /api/auth/logout`
Без изменений: сессия + CSRF, `204`, cookie очищается, сокеты закроются `4401` в течение ≤ 30 с.

### 2.5. `POST /api/auth/logout-all`
Сессия + CSRF, пустое тело. `204`: удаляются **все** сессии пользователя, включая текущую; cookie очищается; все его сокеты закроются `4401` в течение ≤ 30 с. Клиент после ответа показывает экран входа.

### 2.6. `PATCH /api/me`
Сессия + CSRF.
```json
{ "firstName": "Иван", "lastName": "Петров" }
```
- Хотя бы одно поле. `firstName` — 1..64 после `trim`; `lastName` — 0..64 после `trim` (пустая строка допустима). Лишние поля — `400`.
- `200` + `SessionUser`.
- `400 validation_failed` + `details`.
- WS-событий нет: другие пользователи увидят новое имя при следующем чтении (`GET /api/users`, `GET /api/chats`, `GET /api/chats/:id`).

### 2.7. `POST /api/me/password`
Сессия + CSRF.
```json
{ "currentPassword": "old one", "newPassword": "new long passphrase" }
```
- `204`: пароль сменён; **все остальные** сессии пользователя удалены (их сокеты закроются `4401`); текущая сессия и её `csrfToken` остаются.
- `401 auth_failed` — неверный текущий пароль. Сессия при этом жива, это не выход из системы.
- `400 validation_failed` + `details` — `newPassword` не проходит политику (§4.2).
- Лимит неудачных попыток — тот же счётчик по логину, что и у входа (§6): `429`.

### 2.8. Админка
- `GET /api/admin/users`, `PATCH /api/admin/users/:id` — без изменений по поведению; в `AdminUserItem` добавляются `login`, `firstName`, `lastName`.
- `POST/GET/DELETE /api/admin/invites*` удаляются.
- Первый админ: CLI `npm run admin:promote <login>` выставляет `is_admin` существующему пользователю (вместо `npm run admin:invite`); отключённому пользователю отказывает. Снятие прав — через `PATCH /api/admin/users/:id`.

### 2.9. Удаляются
- `POST /api/auth/passkey/login/options`, `…/login/verify`, `…/register/options`, `…/register/verify`.
- `POST /api/invites/inspect`.
- `GET/POST/PATCH/DELETE /api/me/passkeys*`.
- `POST/GET/DELETE /api/admin/invites*`.
- Cookie `wa_ceremony`.

## 3. Модели
| Модель | Поля |
|---|---|
| `SessionUser` | `id`, `login`, `firstName`, `lastName`, `name`, `avatarUrl` |
| `UserSummary` | без изменений: `id`, `name`, `avatarUrl` |
| `ChatMemberDto`, `peer` | без изменений (`name` вычисляемое) |
| `AdminUserItem` | `id`, `login`, `firstName`, `lastName`, `name`, `avatarUrl`, `isAdmin`, `disabledAt` |

- `name` = `trim(firstName + " " + lastName)`, вычисляется сервером. Клиент для отображения использует `name`; `firstName`/`lastName` нужны только форме настроек.
- `login` отдаётся только самому пользователю (`SessionUser`) и админу (`AdminUserItem`). Другим пользователям логин не виден.
- `avatarUrl` — всегда `""` (загрузка аватара вне рамок).
- Удаляются `PasskeyItem`, `InviteItem`, `IssuedInvite`.

## 4. Правила полей

### 4.1. Логин
- Сервер делает `trim` и приводит к нижнему регистру, затем проверяет `^[a-z0-9._-]{3,32}$`.
- Уникален после нормализации: `Alice` и `alice` — один логин.
- Сменить логин нельзя.

### 4.2. Пароль
- Длина 12..256 **байт** UTF-8, без нормализации и без `trim`; длиннее не обрезается, а отклоняется.
- Правил состава (цифры, регистр, спецсимволы) нет.
- Пароль из локального списка частых паролей отклоняется (`too_common`). Сравнение без учёта регистра. Список — `xato-net-10-million-passwords-1000000.txt` из danielmiessler/SecLists (MIT), в репозитории только строки длиной ≥ 12 байт (~46 тыс.).
- Хранится как argon2id (m=19456 КиБ, t=2, p=1) в формате PHC: `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`. PHC-строка с параметрами выше m=65536, t=10, p=4 при проверке считается неверной без вычисления.

### 4.3. Имя
- При регистрации: `firstName` — случайное русское прилагательное, `lastName` — животное, род согласован («Сонный Енот», «Дерзкая Выдра»). Пара уникальна среди всех пользователей: до 5 попыток выбрать незанятую, затем к `lastName` добавляется числовой суффикс 2..999 («Енот 42»). Словари — ~100 прилагательных (мужская и женская форма) и ~100 животных с родом.
- Уникальность случайной пары — «по возможности»: уникального индекса нет (заданные пользователем имена не уникальны), поэтому при одновременных регистрациях совпадение возможно и допустимо.
- Заданные пользователем имена не уникальны.

## 5. Ошибки
Формат прежний, у `400` добавляется необязательное поле `details`:
```json
{ "error": { "code": "validation_failed", "message": "…",
  "details": [ { "field": "password", "code": "too_short" } ] } }
```
| `details[].code` | Где |
|---|---|
| `required` | любое обязательное поле отсутствует или пустое |
| `invalid_format` | `login` не проходит формат §4.1 |
| `too_short` | `password`/`newPassword` < 12 байт, `firstName` пустое после `trim` |
| `too_long` | `password`/`newPassword` > 256 байт, `login` > 32, `firstName`/`lastName` > 64 |
| `too_common` | пароль из списка частых |

`details` есть только у ошибок полей auth/профиля; у остальных `400` поля нет. Клиент не должен зависеть от `message`.

Изменения в таблице кодов `docs/client-integration.md` §1.3:
| `error.code` | HTTP | Когда |
|---|---|---|
| `auth_failed` | 401 | неверный логин или пароль при входе; неверный `currentPassword` при смене пароля. Сессия (если была) **жива**; это не выход из системы |
| `login_taken` | 409 | логин уже занят при регистрации (новый код) |
| `user_disabled` | 403 | вход отключённого пользователя (только после верного пароля) |
| `rate_limited` | 429 | плюс лимит неудачных входов по логину (§6) |
| `invite_invalid`, `reauth_required`, `last_passkey` | — | удаляются |

## 6. Лимиты
| Что | Значение |
|---|---|
| Публичные `POST` (`register`, `login`) | 20 запросов / 60 с на IP (`AUTH_RATE_PER_MINUTE`), общий бакет, как сейчас |
| Неудачные проверки пароля по логину (`login`, `me/password`) | 10 за 15 минут на логин, затем `429` + `Retry-After` до конца окна; вечной блокировки нет; счётчик в памяти процесса |
| Логин | 3..32 символа `[a-z0-9._-]` |
| Пароль | 12..256 байт UTF-8 |
| `firstName` / `lastName` | 1..64 / 0..64 после `trim` |
| Сессия | 400 дней, скользящая (§7) |

Счётчик по логину: считаются и неудачи по несуществующим логинам (иначе ответ выдаёт существование логина); успешный вход сбрасывает счётчик; записи с истёкшим окном удаляются из памяти (иначе при открытой регистрации карту раздувают произвольными логинами).

Для несуществующего логина сервер всё равно вычисляет хэш (против фиктивного значения), чтобы время ответа не выдавало существование логина.

## 7. Сессия
- `SESSION_TTL_DAYS` = 400 (максимум, который браузеры принимают для срока cookie).
- Скользящий срок: если при запросе под сессией до истечения осталось меньше `TTL − 1 сутки`, сервер продлевает `expires_at = now + TTL` и заново ставит cookie `sid` с новым `Expires`. Запись в БД — не чаще раза в сутки на сессию.
- Пользователь разлогинивается только сам (`logout`, `logout-all`), сменой пароля в другой сессии, отключением админом или после 400 дней без единого запроса.
- WS-рукопожатие (`GET /ws`) сессию **не** продлевает: cookie в ответе `101` ненадёжна; продление происходит на REST-запросах (клиент при старте вызывает `GET /api/auth/session`).
- WS: проверка сессии на тике heartbeat смотрит на `expires_at` из БД, а не на срок, запомненный при рукопожатии.
- Правило «сессия не старше 10 минут» (`REAUTH_WINDOW_MS`) удаляется вместе с passkeys.

## 8. Конфигурация
- Удаляются: `CEREMONY_TTL_MS`, `INVITE_TTL_HOURS`, `REAUTH_WINDOW_MS`, `RP_NAME`.
- Меняется: `SESSION_TTL_DAYS` по умолчанию 400.
- `package.json`: `engines.node` `>=24.7` (встроенный `crypto.argon2`).

## 9. Схема БД
Одна миграция без переноса данных (реальных пользователей нет):
- `users`: добавить `login text NOT NULL UNIQUE` (CHECK: равен `lower(login)` и соответствует формату §4.1), `password_hash text NOT NULL`, `first_name text NOT NULL`, `last_name text NOT NULL DEFAULT ''`; удалить `webauthn_user_id`; `name` остаётся колонкой и хранится производным значением `trim(first_name || ' ' || last_name)`: сервер обновляет его при регистрации и `PATCH /api/me`, поэтому чтение чатов, участников и WS-событий не меняется.
- Удалить таблицы `passkeys`, `webauthn_challenges`, `invites` и enum `InviteKind`.
- `sessions` — без изменений схемы.
